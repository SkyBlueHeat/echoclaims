# Incident Model

## Overview

An **Incident** is the central domain record representing a single loss event for a player.
Each incident links pre-event and post-event inventory snapshots, captures contextual
metadata (cause, killer, coordinates), and carries a deduplication key to prevent
duplicate persistence of the same event.

## Domain Record

```java
public record Incident(
    UUID id,
    IncidentType type,          // PLAYER_DEATH (extensible)
    UUID playerUuid,
    long occurredAt,            // epoch millis
    String worldId,             // lowercase world name
    Coordinates coordinates,    // nullable
    String cause,               // e.g. "FALL", "ENTITY_ATTACK", "UNKNOWN"
    UUID killerPlayerUuid,      // nullable
    String killerEntityKey,     // e.g. "minecraft:zombie"
    UUID preEventSnapshotUuid,  // mandatory: links to pre-death snapshot
    UUID postEventSnapshotUuid, // nullable: set after respawn capture
    IncidentStatus status,      // OPEN (extensible)
    Map<String, String> metadata,
    String deduplicationKey     // SHA-256 based, unique constraint in DB
) {}
```

## Lifecycle

1. **Capture**: `DeathCaptureService` captures a pre-death `InventorySnapshot` on the
   main thread during `PlayerDeathEvent`, then builds an `Incident` linking to that
   snapshot.

2. **Persistence**: `EvidencePersistenceService` submits the snapshot + incident pair
   to `EvidenceStore.insertDeathEvidence()`, which atomically inserts both in a single
   SQLite transaction. If the deduplication key already exists, the entire transaction
   is rolled back and the duplicate is counted.

3. **Post-event link**: On `PlayerRespawnEvent`, a post-respawn snapshot is captured
   and linked to the existing incident via `EvidenceStore.insertPostRespawnSnapshot()`,
   which atomically inserts the snapshot and updates the incident's
   `post_event_snapshot_uuid` in a single transaction.

4. **Query**: Administrators query incidents via `/echoclaims incidents <player>` and
   `/echoclaims incident <uuid>` commands, which delegate to `EvidenceLookupService`.

## Deduplication Key

The deduplication key is generated by `DeduplicationKeyFactory.forPlayerDeath()` using:

- Player UUID
- Incident type
- 1-second time bucket (`occurredAt / 1000`)
- World ID (lowercase)
- Coordinates (x, y, z)
- Death cause (e.g. "FALL", "ENTITY_ATTACK")
- Snapshot fingerprint (SHA-256 of item material keys, amounts, slots, and scores)

All components are concatenated and hashed with SHA-256, then hex-encoded. The
`incidents` table enforces uniqueness on `deduplication_key` via a `UNIQUE` constraint.

## Database Schema

```sql
CREATE TABLE incidents (
    id                       TEXT PRIMARY KEY,
    incident_type            TEXT NOT NULL,
    player_uuid              TEXT NOT NULL,
    occurred_at              INTEGER NOT NULL,
    world_id                 TEXT NOT NULL,
    x                        INTEGER,
    y                        INTEGER,
    z                        INTEGER,
    cause                    TEXT NOT NULL DEFAULT '',
    killer_player_uuid       TEXT,
    killer_entity_key        TEXT NOT NULL DEFAULT '',
    pre_event_snapshot_uuid  TEXT NOT NULL,
    post_event_snapshot_uuid TEXT,
    status                   TEXT NOT NULL,
    metadata                 TEXT NOT NULL DEFAULT '',
    deduplication_key        TEXT NOT NULL UNIQUE,
    FOREIGN KEY (pre_event_snapshot_uuid) REFERENCES inventory_snapshots(id),
    FOREIGN KEY (post_event_snapshot_uuid) REFERENCES inventory_snapshots(id)
);
```

## Indexes

- `idx_incidents_player_time` on `(player_uuid, occurred_at DESC)` — for player queries
- `idx_incidents_type_time` on `(incident_type, occurred_at DESC)` — for type/time range queries

## Extensibility

The `IncidentType` enum currently contains only `PLAYER_DEATH`. Future MVPs may add
`ITEM_DROP`, `CONTAINER_LOSS`, etc. The `IncidentStatus` enum currently contains only
`OPEN`. Future MVPs may add `RESOLVED`, `REJECTED`, etc.
